**Location (read-only):**
`dataset/AI-Powered-Criminal-Network-Analysis-System-main/AI-Powered-Criminal-Network-Analysis-System-main/synthetic dataset/`
*(note: the folder is nested twice and the leaf directory name contains a space — ingestion paths must account for this).*

Generated by `generate_synthetic.py` (Faker `en_IN`, `seed=42`). Five CSVs.

| `calls.csv` | **2,000** | CDR-style call detail records |

### Referential integrity (measured — clean)

- `person_id` 1..500, unique, **no gaps**.
- `phone`, `aadhar`, `name` all **unique** (500/500) → deterministic identifiers.
- **Zero** dangling FKs across calls / transactions / FIRs (all `*_id` values resolve to a person; all `location_id` resolve).
- `city → state` mapping in `locations` is **consistent** (no city maps to >1 state).
- Person `city/state` always matches their `location_id` row (0 mismatches).
- Minor self-references: **2 self-calls**, **0 self-transactions**, **1 FIR where complainant == accused**. (Handle as edge cases, not errors.)

### Ground-truth "criminal rings" (measured)

The generator seeds **5 rings** via `ring_id`; membership:

| ring_id | members |
|---|---|
| 0 | 24 |
| 1 | 30 |
| 2 | 33 |
| 3 | 24 |
| 4 | 31 |
| (none) | 358 |

→ **142 of 500** persons belong to a ring. This is our **labelled ground truth** for validating community detection and (optionally) supervising the risk model.

### Temporal windows (measured)

| Stream | Range | Span |
|---|---|---|
| calls | 2026-07-26 → 2026-08-25 | 29 days |
| transactions | 2026-06-26 → 2026-08-25 | 59 days |
| FIR `date` column | 2026-05-27 → 2026-08-24 | 89 days |
| FIR narrative date | 2026-05-27 → 2026-08-24 | 89 days |

- **Call activity is uniform across all 24 hours** (61–100 calls/hour) → *no* natural day/night burst signal.
- FIR `date` column disagrees with the date inside the narrative in **296 / 300** rows → two independent date signals per FIR (use structured `date` as authoritative; treat narrative date as extracted secondary).

### Financial profile (measured)

- `amount_inr`: min ₹235, median ₹243,945, p90 ₹450,467, p99 ₹496,076, max ₹499,273, mean ₹243,699 → **uniform ~₹100–₹500,000** (no power-law, no round-number clustering).
- Payment `mode` is **uniformly distributed** (IMPS 320, NEFT 313, CASH 299, UPI 296, CARD 272).
- Only **15** txns fall in a 45k–50k "structuring" band → no built-in structuring signal.
- `bank_ref` unique 1500/1500; `duration_sec` uniform 5–3600s (mean 1774); `cell_tower_id` effectively random (1803 unique across 2000 calls).

### Graph structure — union of calls + transactions (measured)

- **All 500 persons are connected** in a **single giant component** (0 isolated nodes).
- Degree: max 24, p90 19, median 14, min 2 — **mean 13.9, stdev 3.8**.
- **top-1% / median degree ratio = 1.64** (a heavy-tailed/scale-free network would be > 3) → the graph is close to **Erdős–Rényi random**; there are **no natural "kingpins" by degree alone**.
- Almost no repeat-contact signal: 1,981 unique call pairs (only 17 repeated), 1,496 unique txn pairs (only 4 repeated); max repeats on any pair = 2.

### Ring signal strength — the important caveat (measured)

Intra-ring connection rates vs a ~6% random baseline for a group of ~30:

| ring | members | intra-call rate | intra-txn rate |
|---|---|---|---|
| 0 | 24 | 3.1% | 3.0% |
| 1 | 30 | 7.1% | 8.9% |
| 2 | 33 | 4.7% | 7.4% |
| 3 | 24 | **10.6%** | **10.2%** |
| 4 | 31 | 5.3% | 6.4% |

→ Only rings **3, 1 (and partly 2)** sit clearly above baseline. **Unsupervised community detection on the raw graph will not cleanly recover the 5 rings.** This shapes the whole graph/risk strategy (see §H, §I): the demo's real strength is **multi-source fusion + entity resolution + explainability**, not the (deliberately weak) synthetic ring structure.

### FIR narrative structure (measured)

- Every one of 300 narratives contains: complainant **name** + **Aadhaar**, accused **name** + **phone** (100% extractable).
- Only **3 distinct templates** (effectively one template + a rare "…known to associate with the complainant's circle" variant present in **5** FIRs — a faint textual ring hint).
- All 300 FIRs are `theft`; FIR `location_id` matches the accused's home location in only 1 case (essentially random).

### Entity coverage vs. Problem Statement

PS asks for: person, phone, **vehicle**, location, **organization**, financial transactions, event.

| PS entity | In dataset? |
|---|---|
| person | ✅ persons |
| phone | ✅ persons.phone / call endpoints |
| location | ✅ locations |
| transaction (financial) | ✅ transactions |
| event | ⚠️ implicit (calls, FIRs, txns are events) |
| **vehicle** | ❌ absent (0 plate patterns in FIR text) |
| **organization** | ❌ absent (0 org keywords in FIR text) |

→ The data model and NLP extractor must support vehicle/organization/weapon as **first-class types**, even though the current CSVs contain none. See §P for the optional "demo enrichment pack" that adds these **without touching the originals**.

## B. Entity / Relationship Model

We fuse the five tables into a **unified property graph**. Everything resolves to typed **entities** connected by typed **relationships**, with every edge carrying **evidence references** (the source row IDs that justify it).

### Canonical entity types

| Entity type | Source | Natural key |
|---|---|---|
| `PERSON` | persons | person_id |
| `PHONE` | persons.phone, (future) call metadata | E.164 phone |
| `AADHAAR` | persons.aadhar, FIR text | 12-digit number |
| `LOCATION` | locations | location_id (city/state + canonical geo) |
| `CELL_TOWER` | calls.cell_tower_id | tower id |
| `BANK_ACCOUNT`/`BANK_REF` | transactions.bank_ref | ref string |
| `FIR` | firs | fir_id (as an event/document node) |
| `VEHICLE` *(extensible)* | FIR NLP | plate |
| `ORGANIZATION` *(extensible)* | FIR NLP | normalized name |

### Relationship types (with evidence + weight)

| Relationship | Direction | Evidence | Weight driver |
|---|---|---|---|
| `CALLED` | PERSON → PERSON | call_id(s) | call count + total duration |
| `TRANSACTED` | PERSON → PERSON | txn_id(s) | txn count + total amount |
| `NAMED_IN_FIR` | PERSON → FIR (role: complainant/accused) | fir_id | — |
| `CO_ACCUSED` / `CO_LOCATED` | PERSON ↔ PERSON | shared FIR / shared location_id | count |
| `OWNS_PHONE` / `OWNS_AADHAAR` | PERSON → PHONE/AADHAAR | persons row | 1.0 (deterministic) |
| `LOCATED_AT` | PERSON/FIR → LOCATION | location_id | — |
| `USED_TOWER` | CALL → CELL_TOWER | call row | co-tower proximity |
| `SAME_RING` *(ground truth)* | PERSON ↔ PERSON | ring_id | label only (validation) |
| `MEMBER_OF` / `DROVE` *(extensible)* | PERSON → ORG/VEHICLE | FIR NLP | confidence |

### Hidden-relationship discovery (what the PS is really asking for)

The compelling, **demonstrable** links in this dataset are:

1. **Cross-source identity fusion** — the same `person_id` appears as caller, sender, FIR accused, and FIR complainant. A single suspect's *complete* footprint (who they call, who they pay, which crimes name them, where they operate) is only visible after fusing all five files. This is the core "aha".
2. **Entity resolution from text → structured** — an Aadhaar/phone extracted from FIR free text links back to a concrete person node (deterministic exact match; both are unique keys). This turns unstructured intelligence into graph edges.
3. **Co-location clustering** — 142 persons share a `location_id` with at least one other person → latent co-location communities.
4. **Weighted multiplex proximity** — combining call frequency + money flow + co-location + FIR co-mention amplifies the (weak) ring signal enough to surface plausible clusters, validated against `ring_id`.

## C. Data Quality Findings

These directly change engineering decisions. Each has a mitigation.

| # | Finding (measured) | Impact | Mitigation |
|---|---|---|---|
| **DQ-1** | **Latitude/longitude are random**, uncorrelated with the `city` label — median error **1,513 km**, 0/200 within 50 km of the named city. | Plotting raw coords scatters points into the ocean/Himalayas → map looks broken. | **Geo-normalization layer:** map each `location` to a **canonical city centroid** (10-city lookup) + deterministic small jitter. Keep raw coords as a stored field, never used for display. |
| **DQ-2** | **Multi-line addresses**: 256/500 `address` values contain embedded `\n`. | Naive line-based parsing overcounts persons (757 vs 500); breaks CSV split. | Ingest with a **proper CSV parser** (pandas/`csv` module, quote-aware). Never line-count. |
| **DQ-3** | **Ring signal is weak** (3–10% intra vs ~6% baseline). | Louvain/Leiden won't cleanly recover the 5 rings; demo could look like it "fails". | Present **weighted-multiplex** community detection **and** overlay ground-truth `ring_id`; report modularity + ARI honestly. Frame value as fusion + ER, not ring recovery. |
| **DQ-4** | **Flat centrality** (top-1%/median = 1.64, near-random graph). | Degree alone finds no kingpins. | Combine **multiple** centralities (PageRank, betweenness, eigenvector) + edge weights + ring membership + financial throughput into a composite influence score. |
| **DQ-5** | **Uniform amounts & modes**, no structuring band. | Pure statistical anomaly detection flags an arbitrary tail. | Use **structural** money-laundering patterns (fan-in/fan-out, pass-through chains, cycles) that don't depend on amount distribution; keep amount-based flags as a minor, clearly-labelled signal. |
| **DQ-6** | **Uniform call hours** — no day/night pattern. | "Odd-hour activity" feature won't fire. | Deprioritize odd-hour as a risk feature on this dataset; keep the code path for real data. |
| **DQ-7** | **FIR date ≠ narrative date** in 296/300. | Ambiguous event time. | Use structured `date` as authoritative; store extracted narrative date separately; surface both in timeline with provenance. |
| **DQ-8** | **Templated FIRs** (3 templates, all `theft`, no vehicles/orgs). | NER looks trivial / can't demo vehicle+org extraction. | Rules extractor gives 100% on current text; **also** ship a general NER+regex layer and (optional) enrichment pack (§P) so vehicle/org extraction is demonstrable. |
| **DQ-9** | **Nested dataset path with a space.** | Path bugs on Windows. | Centralize dataset path in config; use `pathlib`, quote paths. |

**Principles**

- **Layered & swappable**: routers → services → repositories. Graph access goes through a `GraphStore` interface so **NetworkX today / Neo4j later** is a config swap. DB access via SQLAlchemy so **SQLite today / PostgreSQL later** is a URL swap.
- **Deterministic, offline-first**: everything (extraction, risk, insights) works with **zero external API keys**; the LLM assistant is an *optional enhancement*, not a dependency.
- **Evidence-linked everywhere**: every derived edge, score, and insight carries the source row IDs that justify it → drives explainability (§I) and audit (§J).
- **Read-only source data**: an ingestion step copies CSVs into the DB; the CSVs are never written.

## E. Backend Architecture

**Stack:** Python 3.14, FastAPI, Uvicorn, Pydantic v2, SQLAlchemy 2.x, pandas (ETL), NetworkX (graph), python-jose + passlib (JWT/hashing). NLP: **rules-first (stdlib `re`)**, spaCy optional. ML: scikit-learn optional (IsolationForest).

**Layering**

```
app/

  core/                   # config, security (JWT/RBAC), logging (PII redaction), db session
  models/                 # SQLAlchemy ORM models
  schemas/                # Pydantic request/response DTOs
  repositories/           # DB access (no business logic)
  services/
    ingestion_service.py  # CSV → DB, geo-normalization, integrity checks
    er_service.py         # entity resolution / unified entity registry
    graph_service.py      # NetworkX build + centrality + communities + paths
    nlp_service.py        # FIR extraction + entity linking
    risk_service.py       # feature engineering + explainable scoring
    anomaly_service.py    # money-mule / cycle / pass-through detection
    case_service.py       # case workspace CRUD + report generation
    audit_service.py      # hash-chain ledger + verification
    insight_service.py    # NL query + auto-narrative (deterministic; LLM optional)
  graph/
    store.py              # GraphStore interface
    networkx_store.py     # default impl
    neo4j_store.py        # stub for later
  api/                    # routers (one per domain)
```

**Cross-cutting**

- **Config** (`pydantic-settings`): dataset path, DB URL, JWT secret, `ENABLE_SPACY`, `ENABLE_LLM`, `LLM_PROVIDER`. Centralizes the awkward dataset path (DQ-9).
- **Security**: JWT bearer auth; RBAC dependency (`require_role("admin")`) — ingestion & audit-verify are admin-only; read/analysis is investigator. Passwords hashed (bcrypt). See §J/security.
- **Logging with PII redaction**: a logging filter masks Aadhaar (`######******`), phone, and full names in logs (PS security requirement — no raw sensitive data in logs).
- **Graph lifecycle**: NetworkX graph built once at startup (or after ingestion) from the DB, cached in memory, rebuilt on `/ingest/run`. ~500 nodes / ~3,500 edges → trivially fits in memory; sub-second analytics.

## G. AI / NLP Strategy

**Design principle:** *high-precision, deterministic, offline-first;* ML/LLM are optional accelerators, not requirements. This suits templated FIRs (DQ-8) and guarantees the demo runs anywhere.

### 1. FIR entity extraction — hybrid, two layers

- **Layer 1 — Rules (default, 100% on current data):** compiled regex for the known template:
  - Aadhaar: `\b\d{12}\b`; Phone: `\+91-\d{10}`; Names: `Suspect (NAME)` / `(NAME) (Aadhar …)`; Crime: `reported a (\w+)`; Place: `at (CITY), (STATE)`; narrative date.
  - Also (for real/enriched FIRs): **vehicle plates** `\b[A-Z]{2}[-\s]?\d{2}[-\s]?[A-Z]{1,2}[-\s]?\d{4}\b`, **organizations** (`Ltd|Pvt|Bank|Trust|Enterprises`), **weapons**, **currency amounts**.
- **Layer 2 — Statistical NER (optional, `ENABLE_SPACY`):** spaCy `en_core_web_sm` for PERSON/ORG/GPE on unstructured text the rules miss. Falls back cleanly if spaCy isn't installed (see §P Python-3.14 risk).

### 2. Entity resolution / linking

- **Deterministic exact match** on Aadhaar + phone (both unique keys in `persons`) → link FIR-extracted identifiers to concrete `PERSON` nodes with confidence 1.0. This is the headline "unstructured → structured" win.
- **Fuzzy match** (RapidFuzz on name + city) for real-world data where exact keys are missing — kept behind a confidence threshold.
- Unified **entity registry** (`entities` table) dedupes by `(type, canonical_value)`.

### 3. Semantic search / investigator assistant

- **Search:** entity index (name/phone/aadhaar/city) + **TF-IDF** over FIR narratives for free-text search. Optional sentence-embeddings if available.
- **Assistant (`/insights/ask`):** deterministic default — a small **intent router** maps NL questions ("how is X connected to Y", "who does X pay", "riskiest people in Mumbai") to graph queries and returns a templated NL answer **plus** the supporting subgraph/evidence. Optional LLM mode (Claude, config-gated) rewrites the same *facts* into fluent prose — the LLM never invents facts, only phrases retrieved evidence (grounded generation).

### 4. Auto-narrative insights

Given an entity, generate a plain-language brief ("Person #X: ring-3 member, 22 contacts, ₹1.2M outflow across 9 transfers, named as accused in 2 FIRs, high betweenness bridging two clusters") from structured facts — deterministic template, optionally LLM-polished.

## H. Graph Analytics Strategy

**Engine:** NetworkX in-memory, built from the DB via the `GraphStore` interface (Neo4j-ready).

### Graph construction — weighted multiplex → analytic projection

- Build a **multi-relational** graph (CALLED, TRANSACTED, CO_LOCATED, NAMED_IN_FIR, OWNS_*).
- For analytics, project to a **weighted undirected** person-person graph:
  `w(u,v) = α·norm(call_count) + β·norm(call_duration) + γ·norm(txn_count) + δ·norm(txn_amount) + ε·co_location + ζ·fir_co_mention`
  Weights amplify the weak ring signal (DQ-3) so clusters become detectable.

### Analytics delivered

| Capability | Method | Endpoint |
|---|---|---|
| **Key suspect / influencer** | composite of PageRank + betweenness + eigenvector + weighted degree (DQ-4) | `/risk/top`, `/graph/metrics` |
| **Community / ring detection** | Louvain via **native `nx.community.louvain_communities`** (weighted, fixed `seed` for determinism — *not* `greedy_modularity_communities`; no extra dependency); **overlay ground-truth `ring_id`**; report modularity + ARI vs labels | `/graph/communities` |
| **Ego network / "show connections"** | k-hop neighborhood (depth 1–3) | `/graph/ego/{id}` |
| **Link between two suspects** | shortest path + all-simple-paths (bounded) | `/graph/shortest-path` |
| **Bridges / cut points** | betweenness + articulation points (brokers between clusters) | `/graph/metrics` |
| **Money-flow subgraph** | directed txn graph for anomaly service | `/anomalies/*` |

**Honesty in the demo:** community results are shown *next to* the ground-truth rings with quantified agreement — this demonstrates rigor and is more credible to judges than a hidden, over-fitted result.

## I. Risk Scoring Strategy

**Approach:** an **explainable weighted-feature model** (transparent by construction) — *not* a black box. Every score decomposes into named factors, each with a contribution and the **evidence records** that produced it. This directly satisfies PS req. 13 (explainable reasons behind every score).

### Feature families (per person)

1. **Network position** — weighted degree, PageRank, betweenness (bridging), eigenvector centrality.
2. **Community** — membership in a detected cluster / ground-truth ring; bridging between clusters.
3. **Financial** — total outflow/inflow, fan-in & fan-out counts, participation in pass-through chains or cycles (see anomalies).
4. **Criminal record** — count/role in FIRs (accused vs complainant), co-accused links.
5. **Association** — number of high-risk direct contacts (risk propagation, 1 hop).
6. **Behavioral** — call bursts, contact diversity. *(Odd-hour deprioritized per DQ-6.)*

### Scoring

- Normalize each feature to [0,1], combine with tunable weights → raw score → **0–100** + tier (`LOW / MEDIUM / HIGH / CRITICAL`).
- Weights live in config (`risk_weights.yaml`) so they're tunable and auditable.
- **Optional** unsupervised cross-check: IsolationForest over the feature matrix flags outliers; agreement with the weighted score raises confidence. (Optional because amounts are uniform, DQ-5.)

### Explainability contract

Each `/risk/{id}/explain` returns:

```json
{
  "entity_id": 137, "score": 78, "tier": "HIGH", "model_version": "1.0",
  "factors": [
    {"name":"High betweenness","contribution":21,"description":"Bridges two clusters (top 5%).","evidence":{"metric":"betweenness","value":0.031}},
    {"name":"Ring member","contribution":18,"description":"Member of detected community C3 (matches ground-truth ring 3).","evidence":{"community":"C3","ring_id":3}},
    {"name":"Money pass-through","contribution":16,"description":"Received ₹4.1L and forwarded 92% within 48h.","evidence":{"txn_ids":[221,489]}},
    {"name":"Named in FIRs","contribution":14,"description":"Accused in 2 FIRs.","evidence":{"fir_ids":[12,205]}},
    {"name":"Risky associates","contribution":9,"description":"3 direct contacts are HIGH risk.","evidence":{"person_ids":[88,301,412]}}
  ]
}
```

### Suspicious relationship / transaction detection (money-laundering typologies)

Structural patterns (amount-distribution-independent, DQ-5):

- **Fan-in / fan-out** (smurfing): many senders → one receiver → many receivers.
- **Pass-through / layering**: A→B→C where B forwards most of what it received within a short window.
- **Cycles**: money returning to origin (`nx.simple_cycles` on directed txn graph).
- **Bridge transactions**: transfers connecting two otherwise-separate clusters.

Each flagged pattern is a first-class object with type, participants, evidence txn_ids, and a severity — surfaced in the UI and feeding the risk score.

## J. Blockchain / Audit Strategy

**Decision:** a **local private hash-chain ledger** (blockchain *concept*, not a public chain). **No sensitive criminal data is ever placed on a chain** — only action metadata + cryptographic hashes.

### Design

- Every significant action (login, ingest, view sensitive entity, create/modify case, add evidence, generate report, run risk) appends an **audit record**:
  `{ seq, timestamp, actor_id, role, action, resource_type, resource_id, payload_hash = SHA256(canonical_payload), prev_hash, this_hash = SHA256(seq|timestamp|actor|action|resource|payload_hash|prev_hash) }`
- Records form a **tamper-evident chain**: altering any record breaks every subsequent `this_hash`.
- **`GET /audit/verify`** recomputes the chain and returns the first broken link (if any) → live **tamper-evidence demo**: edit one row in the DB, verification fails and pinpoints it.
- **Report integrity:** when a case report is generated, compute a **Merkle root** over its evidence items and store a `report_manifest`. Anyone can later re-hash the report and confirm it matches → verifiable, non-repudiable reports.
- **PII-safe:** payloads are hashed; the ledger stores only IDs + hashes + action metadata, never raw Aadhaar/phone/narrative.

**Extensibility:** the `AuditLedger` interface can later be backed by a permissioned ledger (e.g., Hyperledger) without changing callers — but the hash-chain fully satisfies the SIH "immutable audit trail" requirement offline.

## R. As-built — Phase 3 shipped: FIR Narrative NLP (addendum, 2026-08-26)

*Appended after Phase 3. Prior sections are unchanged; where this section refines §G's
plan, it says so explicitly. Full detail, rule inventory, worked examples and limitations
live in [`docs/phase3_nlp.md`](phase3_nlp.md).*

Phase 3 implements `backend/app/nlp/` and serves `/api/v1/nlp`. The pipeline is
`FIR text → preprocessing → entity extraction → normalization → entity resolution →
relationship extraction → validation → evidence-backed graph integration`, and it is
**100% deterministic and offline**: zero new dependencies, no model download, no external
API, no learned parameter.

**How this refines §G.** §G.1's Layer 1 (rules) is built in full and is the *only* active
path. §G.1's Layer 2 (spaCy) is **not** a dependency — `spacy_available()` exists solely
so the absence is explicit and reported by the API (`optional_spacy_model_available:
false`); a test asserts `spacy` is never imported. A `SupplementalExtractor` protocol is
the documented extension point, so a future local model passes through the same span-dedup
and validator gate rather than bypassing the deterministic core. §G.2's exact-key
resolution is built (Aadhaar/phone/name); **fuzzy/RapidFuzz matching was deliberately not
added** — with unique keys on this dataset it would only invent risk. §G.3's TF-IDF
semantic search and §G.4's auto-narrative insights remain future work; `/nlp/search` is
deterministic substring matching over mention text, normalized values and resolved ids.

**Isolation from Phase 2 (the load-bearing invariant).** Narrative edges live in a
**separate `NetworkXGraphStore`** owned by `NarrativeGraphIntegrator` and typed by
`NarrativeEdgeType`, an enum distinct from `EdgeType`. Phase 2's `EdgeType` /
`ALLOWED_EDGE_TYPES` were not touched, and the structured store is **read-only** to
Phase 3 — used for duplicate and derivability checks, never written. Provenance keeps the
two kinds distinguishable at a glance: narrative edges carry `is_narrative: true`,
`source_dataset: "fir_text"`, evidence ids `firs:{id}`, and ids prefixed `narr~`. Their
`weight` is fixed at 1.0 with `weight_detail.note: "not an analytic coefficient"`, so
narrative edges can never be mistaken for analytic input. The `SAME_RING` ground-truth
overlay is excluded from every check (`include_overlay=False`), and two tests prove no
ground truth leaks into the "is this link already known?" accounting.

**Every proposed edge gets exactly one explainable disposition:** `accepted_new` (new
connectivity), `accepted_additive` (new type, endpoints already connected within
`nlp_derivability_max_hops = 2`), `accepted_merged` (new provenance on an existing edge;
confidence = **max**, never averaged), `rejected_duplicate`, `rejected_self_loop`,
`rejected_unresolved`, `rejected_low_confidence` — each with a prose reason exposed at
`/nlp/firs/{id}/graph-impact`.

**Confidence semantics (extends decision Q.1).** Q.1 deferred Tier C (FIR free-text) to
this phase. As built, Tier C is a small set of **deterministic rule-assigned tiers, not
learned probabilities**: extraction `regex/known_record = 1.0`, `anchored_pattern = 0.6`;
resolution `identifier/unique-name = 1.0`, `fir_context = 0.9`; relationship
`explicit = 1.0`, `hedged/anaphoric = 0.9`, `soft placement ("near") = 0.7`. The table is
served at `/nlp/summary` so no consumer has to guess. Ambiguous mentions are **never
silently merged** — they are listed with all candidates and refused as edge endpoints.

**Measured results (300 FIRs).** 1,800 entities — PERSON 600, PHONE 300, AADHAAR 300,
LOCATION 300, DATE 300; MONEY / VEHICLE / ORGANIZATION **0** (supported as first-class
types, absent from this corpus — confirming §A's entity-coverage finding, and reported as
an honest zero). Resolution: 1,500 resolved, 300 not-applicable (DATE has no graph node
type), **0 unresolved, 0 ambiguous** — because names, phones and Aadhaar numbers are
unique here, so no ambiguous mention exists; those branches are covered by synthetic unit
tests instead. 605 relationships — REPORTED_AGAINST 300, LOCATED_AT 300,
ASSOCIATED_WITH 5 (the "known to associate with the complainant's circle" variant from
§A); MET / CALLED / TRANSFERRED_TO **0**, implemented but never triggered by these
templates. Narrative graph: 381 nodes / 304 edges from 299 source records. Nothing was
dropped by validation at either stage.

**The honest headline (DQ-8, and the answer §G owed).** Of 605 proposed relationships,
